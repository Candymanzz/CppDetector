# CppDetector — план действий (v2)

C++ приложение для инспекции кадров методом сравнения с эталоном (без машинного обучения).
10 камер, у каждой свой эталон. Раз в заданный период приходит пачка из 10 кадров (по одному с каждой камеры), обрабатывается параллельно, результат показывается в веб-интерфейсе.

## 1. Что выяснили про данные и окружение

**Принципы:** делаем с нуля; всё, что относится к Python, старым сервисам и прошлому опыту, игнорируем. Файлы `result.json` и `heatmap.u8` в папках кадров не читаем и не используем — берём только `frame.jpg`.

**Данные** (`D:\GitHubPj\CppDetector\frame\frame`, в `.gitignore`; кадры уже уменьшены, поэтому `downscale` по умолчанию = 1.0):
- `camera_0 … camera_9`, в каждой по 20 папок-кадров `f_XXXXXXX/`, внутри `frame.jpg` (960×803), `result.json`, у камер 0–5 ещё `heatmap.u8` (384×321, gray u8).
- Номера кадров у разных камер разные, поэтому кадры берём **по порядку внутри камеры**: самый ранний = эталон, следующие = проверяемые.
- Старые `result.json` — вывод предыдущей (Python) системы: у камер 0–5 всё `REJECT`, score=1.0, у камер 6–9 `NO_REFERENCE`. Это **не эталонная разметка**, ориентироваться на них как на «правду» нельзя. Можно использовать только как справку.
- Сцены: камеры 0–5 смотрят на белое ведро (тёмный фон, кадры почти идентичны), камеры 6–9 — другой ракурс, сильные засветы (пересвеченная белая область, мало деталей). Для 6–9 порог/чувствительность, скорее всего, нужно подбирать отдельно.

**Окружение:**
- Есть: CMake 4.3, Git, **MSVC 14.44 (Visual Studio Build Tools 2022)** — компилятор у тебя уже стоит, ничего ставить не нужно.
- Нет: vcpkg, OpenCV для C++ (Python-овский не подходит; Python в PATH, судя по всему, вообще нет).
- План: я сам клонирую vcpkg и собираю OpenCV (только нужные модули, чтобы было быстро и компактно). Место на D: освободили (90 ГБ) — vcpkg ставим в **D:\vcpkg** (вне репозитория). Сборка идёт 20–40 минут, это разовая операция.

## 2. Цели

- Для каждой из 10 камер — свой эталон (по умолчанию самый первый кадр камеры, можно перевыбрать).
- Эмуляция «настоящей» инспекции: с периодом `period_ms` (настраивается) подаётся очередной кадр каждой камеры и сравнивается с эталоном этой камеры.
- Результат на кадр: **score аномалии (%)**, **зона аномалий** (heatmap + контуры), вердикт **OK / БРАК**.
- Бюджет времени: вся пачка из 10 кадров обработана **за ≤ 500 мс** (цель 300–450 мс). *(Ты написал «500 секунд» — считаю, что это 500 миллисекунд.)*
- Веб-интерфейс для теста и настройки.
- Лог решений и причин брака.
- База знаний на английском, в нескольких файлах.

## 3. Параметры

Глобальные (в `config.json`, часть меняется из UI):

| Параметр | Смысл |
|---|---|
| `source_dir` | Корневая папка с кадрами |
| `period_ms` | Период подачи пачки (эмуляция частоты инспекции) |
| `downscale` | Коэффициент уменьшения кадра перед обработкой (1.0 = оригинал, 0.7 = −30%) для выигрыша во времени |
| `threads` | Число рабочих потоков |

На камеру (`cameras[i]`):

| Параметр | Смысл |
|---|---|
| `reference` | Файл эталона |
| `roi` | Полигон ROI (точки), в координатах оригинала |
| `sensitivity` | Чувствительность сравнения |
| `reject_threshold` | Порог брака, %: `score > порог` → БРАК |
| `shift_tolerance` | Допуск на микросдвиг (px) — см. ниже |

## 4. Алгоритм инспекции (OpenCV, классический CV)

1. Downscale кадра и эталона (INTER_AREA).
2. **Лёгкое позиционирование**: phase correlation (`cv::phaseCorrelate`) — только сдвиг, очень дёшево. Если сдвиг > допуска — это отдельная причина в логе (`shift_exceeded`), иначе кадр сдвигается обратно. Тяжёлый ORB/ECC не используем (по скорости).
3. **Допуск на микросдвиги**: при сравнении берём «минимальную разницу в окрестности» — разница кадра с эталоном, расширенным (dilate/erode min/max) на `shift_tolerance` px. Края, сдвинувшиеся на 1–2 px, не дают ложного брака.
4. Нормализация яркости внутри ROI (учёт дрейфа экспозиции; критично для засвеченных камер 6–9).
5. Разница (absdiff в Gray/Lab) + blur → карта различий.
6. **Sensitivity** → порог бинаризации (выше чувствительность = ниже порог).
7. Морфология, отсечение мелких пятен (`min_blob_area`).
8. **Score** = доля аномальных пикселей **внутри ROI** (%).
9. Вердикт: `score > reject_threshold` → БРАК.
10. Визуализация: heatmap-наложение + контуры/bbox зон аномалий.

## 5. Автоопределение ROI (ускорение настройки)

Ручной ROI — полигон по точкам (клики на эталоне). Плюс кнопка **«Авто-ROI»**, которая предлагает контур, а человек правит:
- Алгоритм (дешёвый, разовый, на этапе настройки, не в горячем цикле): downscale → blur → Otsu/адаптивный порог по яркости (ведро светлое на тёмном фоне) → морфология → самый крупный контур → `approxPolyDP` до 8–20 вершин.
- Для камер 6–9 (засветы) возможны другие подходы (градиенты/GrabCut) — проверим на реальных кадрах и зафиксируем в KB, что работает.
- В UI вершины можно таскать, добавлять, удалять; итог сохраняется в конфиг.

## 6. Архитектура

```
FrameSource (frame/camera_N/…) ─► BatchScheduler (period_ms: по 1 кадру с каждой из 10 камер)
                                       │
                                       ▼
                               ThreadPool ─► Inspector[cam] (эталон + ROI + параметры)
                                       │
                                       ▼
                    DecisionLogger (JSONL) + WebServer (HTTP/JSON + статика)
```

Модули `src/`: `source/`, `pipeline/`, `inspect/`, `reference/` (эталоны, ROI, авто-ROI), `config/`, `log/`, `web/`.
Стек: C++17, CMake + vcpkg (manifest), OpenCV, cpp-httplib, nlohmann-json; фронтенд — чистый HTML/JS (canvas для рисования ROI), без сборщика.

## 7. Веб-интерфейс

- Выбор камеры, просмотр эталона, рисование/правка полигона ROI, кнопка «Авто-ROI», «Сделать эталоном этот кадр».
- Параметры: sensitivity, порог брака, допуск сдвига, downscale, период (применяются на лету).
- Сетка 10 камер: текущий кадр, score, вердикт, heatmap/контуры, время обработки каждого кадра и всей пачки (с индикацией превышения 500 мс).
- Старт/стоп эмуляции, просмотр лога брака с фильтром по причине.

## 8. Логирование

- `logs/decisions.jsonl` — запись на кадр: время, камера, файл, score, порог, sensitivity, ROI-хэш, вердикт, причина (`score_over_threshold`, `shift_exceeded`, `no_reference`, …), bbox зон, время обработки.
- Картинки брака (heatmap/overlay) — `logs/rejects/`.
- Статистика времени пачки (min/avg/max) — чтобы следить за бюджетом 500 мс.

## 9. База знаний (`docs/kb/`, на английском)
